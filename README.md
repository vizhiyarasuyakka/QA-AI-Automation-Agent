# QA Workflow App

A web application that runs the 13-stage QA workflow for a web product release: intake, AI test design, review gates, environment check, smoke, three execution lanes, exploratory and non-functional stages, bug logging with a webhook to your in-house app, regression, automation runs, sign-off with twelve metrics, and post-release escapes.

Stack: Next.js 15 (App Router, server actions), Prisma 6, PostgreSQL, Claude API for test case generation.

## Setup

1. Prerequisites: Node 20+, Docker (for the bundled PostgreSQL) or any PostgreSQL 14+.
2. Copy the env file and fill it in:

       cp .env.example .env

   - `DATABASE_URL`: leave as is if you use the docker-compose database.
   - `ANTHROPIC_API_KEY`: optional. When empty, generation runs through this machine's Claude Code login, so sign in to Claude Code first. Set a key for any shared or hosted deployment, because a login belongs to one person's machine.
   - `BUG_WEBHOOK_URL` and `BUG_WEBHOOK_TOKEN`: optional, your in-house QA app endpoint. Can also be set later in Settings inside the app.
3. Start the database and the app:

       docker compose up -d
       npm install
       npm run db:push
       npm run dev

   Open http://localhost:3100.

`npm run db:push` creates the tables. For versioned migrations use `npm run db:migrate` instead. `npm run db:studio` opens Prisma Studio to inspect data.

## How the workflow maps to the app

| Stage | Where in the app | Gate |
| --- | --- | --- |
| 1 Requirement docs | Requirement docs: store the PRD, user stories, prototype and module fields | Gate 1: every story has acceptance criteria, computed |
| 2 TC/TD | TC/TD: load the user stories, select them, generate test cases and test data. Story page: generate one story, paste, or add by hand | |
| 3 Test review | Test case review: tick cases, export them to Excel, CSV or an uploaded template or mark them reviewed, export test data, flag smoke and regression | Gate 2: every case reviewed and no coverage gaps, computed |
| 4 AC Check | AC Check: the URL to test and the test account, then every acceptance criterion checked in Chrome | Gate 3: the URL to test is set, computed |
| 5 Smoke | Test case review: cases flagged smoke; their results come from Playwright runs or CI imports | Gate 4: every smoke case passes; met when none is flagged, computed |
| 6 Playwright Test | Playwright Test: specs generated from the test cases and run in a hidden Chrome, or imported from CI; automated flag on cases | |
| 7 API Test | API Test: the API list, positive, negative and edge-case tests written by Claude and sent by Playwright, the request and reply of each as evidence | |
| 8 UI Testing | UI Testing: the prototype compared screen by screen and flow by flow, and the user stories checked on the build, with screenshot evidence | |
| 9 Security Testing | Security Testing: the built-in checks and the OWASP ZAP baseline scan, every check listed with what fails and where | Feeds Gate 5: Done when nothing High or Medium is open |
| 10 Defect logging | Bugs: template fields enforced, reproduce-by-human rule, duplicate check, push through the MCP connector or webhook | |
| 11 Retest and regression | Bugs: Fixed, Reopened; reopen rate | |
| 12 Sign-off | Sign-off page: twelve metrics, Gate 5, report text | Gate 5: computed; Go is refused when not met |
| 13 Post-release | Sign-off page: escapes with the stage that missed them | |

The workflow board on each release shows all 13 stages, the five gates and their reasons, and the headline numbers.

## The flows

Each step shows its status in the release navigation, and the 13-stage board follows the steps: opening the board brings every stage up to date, and only stage 13 (Post-release) is set by hand. Smoke is optional: with no case flagged smoke, Gate 4 counts as met. Settings lists, stage by stage, the free tools each one runs on, where Claude, ChatGPT or a plugin skill comes in, and the connection chosen for it.

1. **Requirement docs.** One form and one list store the PRD, user stories, prototype and module fields, filterable by type and module. Nothing is checked or judged here and no model runs. Text is extracted at upload from PDF, DOCX, XLSX, CSV, TXT and MD. Prototype screens are read as pictures or files by Claude, so they need the Claude login. Images inside other documents and scanned PDFs are not read: a scanned PDF shows as Failed and later steps skip it until it is replaced.
2. **TC/TD: test cases and test data.** Nothing is checked first and a PRD is optional. Load user stories makes one request that lists the stories in the user stories files; a PRD is never used for this, and a note shows when a user stories file changed after that. The Test case prompt section holds the instructions Claude follows when writing cases and test data; it can be edited or reset, applies to the next generation in every release, and the app always adds its own rules for reading files, numbering steps and tagging coverage. The page shows one row per file with its stories inside: tick the file to select them all, or open it and tick some. A loader shows while a run is going; afterwards only what went wrong is shown. PRDs are listed below, unticked, and a ticked PRD goes to Claude with every selected story. On first generation a story's acceptance criteria and fields are read from its files. A story whose criteria are already filled needs no file at all. The server computes what is uncovered (`src/lib/coverage.ts`), asks for those cases, and repeats until nothing is missing or progress stops. Whatever remains is reported as gaps. Each case carries the exact values to enter, and each story gets a test data sheet of valid, invalid, boundary and empty values. Add a test case by hand takes a story, a title, the criteria it covers, steps, test data and the expected result; a blank TC ID takes the story's next number. The page lists the cases created for each story. Re-running only adds what is missing and never changes existing cases; the sheet is rebuilt when cases were added. Delete selected removes the ticked stories with their cases and test data; loading again brings them back if the file still names them. When the plan limit is hit a run stops there and keeps what it finished.
3. **Test case review.** Story by story or a whole module at a time: tick the cases, then export them to Excel, CSV or an uploaded template to review outside the app, or mark them reviewed here; nothing needs approving. The whole release can also be exported from this step: test cases to Excel, CSV or an uploaded template, and test data to Excel or CSV. No model runs in this step. Every case reaches execution. Nothing is signed: Gate 2 is met once every case is reviewed and the server finds no coverage gaps.
4. **AC Check.** Enter the URL to test and, when the app needs one, a test account. Run all criteria checks every acceptance criterion of every story in one run, one story after another; Run the ones not passed carries on after a stop. Or choose a user story and press Run on one criterion or Run all of that story. No test cases are needed. Claude in Chrome opens the URL in a new tab of the user's Chrome, signs in on the app's own sign-in page when it asks, stays on that site, and checks each criterion the positive way: the normal path with valid input. Each criterion shows Pass, Fail or Blocked with what Claude saw, and can also be marked by hand. A failed criterion becomes a bug draft. A story with no criteria yet can fetch them from its user stories file with one request, and criteria can be added by hand, one per line, numbered after the story's last one. Claude in Chrome driven from Claude Code refuses localhost and private network addresses, so for those the run opens a Chrome window of its own on this machine (Playwright, the same tool as step 5), signs in there and checks the criteria. The run needs Chrome open with the extension signed in to the same account as Claude Code; when it is not connected or a site is not allowed, the run stops and says so. The URL and sign-in are kept for the release; the password is never shown again and is sent to Claude with each run, so use a test account.
7. **UI Testing.** Using the prototype from step 1 (PNG, JPG, WEBP, HTML or SVG, one file per screen), the app opens each screen of the URL to test (the same URL and test account as step 4) in a hidden Chrome on this machine, signs in on the app's own sign-in page when a password field shows, and compares it with the prototype using free, open-source tools only, so no Claude plan is used. Playwright draws both pages at the same width (1440 unless another is chosen; a picture prototype keeps its own size, and a 2x or 3x export counts as the same design), and pixelmatch, the pixel check Playwright itself uses, counts the changed pixels and draws them in red. At most 0.5% changed is a Match. For an HTML prototype every form field is checked as well: which of the prototype's fields the build is missing, which fields the build has that the prototype does not, and for the same field its label, kind (text box, dropdown, checkbox and so on) and required star. Fields are matched by the label or placeholder a person sees, then by kind and place, so a field moved down by a longer list is still found. A field difference always counts, however few pixels it changes. Every text on both pages is compared too: missing, extra or reworded, and for the same text its colour, background, font, size and place. Only what is shown counts: a panel faded out or covered by another is ignored, and the screenshot waits until loading placeholders are gone. Table cells, fields inside table rows and numbers are sample data and do not count. Give a screen's page, or leave it blank and the app follows a link or button named like the screen from wherever signing in lands. Compare one screen, all of them, or those not matching. Every difference is numbered and has screenshot evidence: a close-up of the prototype and of the build with the spot boxed, a dashed "not here" box where an element is absent, and one evidence picture with the prototype and the build side by side and every difference marked. The changed pixels stay below to check by eye. A Mismatch becomes a bug draft that lists the differences by number and links to the evidence picture. With Follow the prototype's flows ticked, each screen's flows are compared too: the first time a screen is compared, the app clicks through its HTML prototype (up to three minutes) and keeps every state a click opens, two clicks deep, such as the form New Account opens, a row's detail view and its tabs, a filter panel, a board view or a row menu. Side bar links lead to other screens and are not followed, and controls named after a record (an account, a stage, an owner) are sample data. Nothing that saves, deletes, sends, imports, exports or signs out is ever clicked, on the prototype or on the build. Each flow is then clicked the same way on the build, from the screen's page, and what it opened is compared field by field and text by text, leaving out what the screen already showed, with the same numbered close-ups and evidence picture. A control the build does not have by that name stops the flow and is itself the difference, with the build's picture showing where it stopped. Each flow's bug draft lists the clicks to repeat it. Find flows again forgets a screen's flows so the next comparison finds them anew, a flow that is not wanted can be removed, and uploading a prototype again finds its flows again. Compare on one screen, or Check this flow again on one flow, opens that screen on its own, with a loader at the top while it runs: the step being checked, a progress bar, and each flow marked done, being checked or waiting, its result showing as soon as it is checked. The other screens and the settings fold away below it, and Show all screens brings them back. A PDF prototype cannot be compared pixel by pixel. Without a test account a screen behind a login reads as Blocked. Each screen can also be marked by hand. Below the screens, Does the build do what the user stories say? checks the build against the stories instead of the prototype. Write the checks first maps the build (signed in with the test account, its navigation followed page by page, up to 40 pages, nothing clicked but links, each page's buttons, tabs, fields and table columns read), then Claude turns each story's acceptance criteria and field rules into flows (a page and the clicks that open a form, filter panel or detail view on it, using the names the map shows) and checks: every field the story names with its kind and required mark, the choices of its dropdowns and filters, the buttons and texts it mentions, and one validation check for each mandatory field and each min, max or format rule. Check them on the build runs them with Playwright only: a field is found by the label a person reads, else its placeholder or hidden name, else a control beside a matching label (a date picker made of a button); a dropdown is opened, its choices read and closed again; a validation check opens the form afresh, fills the other mandatory fields, leaves the target empty or puts its bad value in, presses the save button the story names and passes when an error shows at the field or names it, the field is marked invalid, or the browser stops the save, and fails when nothing shows, saying so when the form closed and the record may have been saved. Press Save to check validation errors can be turned off; Delete, Send, Approve and the like are never pressed. Each check shows what the build showed, and failed ones are boxed and numbered on the flow's evidence picture, with a close-up; a validation check keeps its own picture after pressing save, and a dropdown its picture while open. A step the build has no control for stops the flow as Blocked with a picture of where it stopped, and a flow's page and steps can be corrected by hand. A flow that differs from its story becomes a bug draft linked to the story, High when a record could be saved without a mandatory value. Write its checks again and Check this story or Check this flow work on one at a time. Further down, Find triggers lists every action a user can take on each screen and Run UI test tries each one; those two use Claude.
6. **API Test.** Paste or upload the API list: one endpoint per line starting with its method, with its notes after the path and on the lines under it and a `#` heading as a group; or a CSV with a method column; or a Postman collection (JSON) or an OpenAPI document (JSON or YAML), whose folders, tags and request schemas become groups, notes and sample bodies. Enter the base URL (the URL to test's origin is suggested), the sign-in header and its value (kept on this machine and never shown again) and variables, written as `{{name}}` in the tests. Claude writes for each endpoint one or two positive tests, three to five negative tests (a missing field, a wrong type, an unknown id, broken JSON, no sign-in, each expecting a 4xx) and two to four edge tests (empty and longest values, boundary numbers, unicode, huge page sizes, repeats), from the notes and from the field rules the stories carry; DELETE and anything named delete, remove or reset get no positive test, so nothing real is removed. Tests are numbered after their endpoint, API-003-02. Run all tests sends them from this machine with Playwright Test, no browser, two at a time. Each test shows Pass, Fail or Blocked (the API could not be reached, or a variable it needs is not set), the time it took, and the exact request and reply with the sign-in value hidden, also at a text address the bug drafts link to. A failed test becomes a bug draft with the request as its steps and the reply as what happened; a later pass clears a draft nobody has acted on. Download the Playwright project (config, helpers, one spec per endpoint, a README) to run the same tests elsewhere and post the results to `/api/import/playwright`, or download a Postman collection with the same tests as `pm.test` scripts to run in Postman or Newman and post to `/api/import/newman`. Adding the list again adds only endpoints that are new; Write its tests again replaces one endpoint's tests; a wrong test or an endpoint outside the release can be removed. The page ends with a how-to covering all of this.
5. **Playwright Test.** Writes one spec per story from its step 2 test cases (split every 20 cases), checks that it parses, and stores it. Run the scripts here runs every stored spec with Playwright Test in a hidden Chrome on step 4's URL to test, signed in with step 4's test account (passed to the scripts as QA_USER and QA_PASSWORD), then records each result on its test case, with what happened and the screen at the end of the test as evidence, and counts the run towards automation stability. Run by user story works the way AC Check does: choose a story from the list, generate its scripts alone, run the whole story or one test case (Playwright is told to run only the test titled with that TC ID), and see each case with its expected result, Pass or Fail, what happened and its screenshot; failed cases become bug drafts that link to the screenshot, and a case that passes again clears its draft. Test titles start with the TC ID, so results posted to `/api/import/playwright` map back to the case (without screenshots, which only a run on this machine keeps). The scripts have not seen the running application, so lines marked `// VERIFY` need checking on the first run.
8. **Security Testing.** Run security scan looks at the URL to test with free tools and lists every check with Pass, or its risk, where it was seen, what was found and how to fix it. The built-in checks open the site in a hidden Chrome, sign in with step 4's test account and visit the mapped pages (up to 15): HTTPS, the Strict-Transport-Security, Content-Security-Policy, X-Frame-Options or frame-ancestors, X-Content-Type-Options, Referrer-Policy, Permissions-Policy and Cache-Control headers, Server and X-Powered-By disclosure, CORS with credentials, the HttpOnly, Secure and SameSite flags of the cookies set after signing in, mixed content and forms posting over HTTP, password field autocomplete, whether `/.git/HEAD`, `/.git/config` or `/.env` are served, whether redirect-style parameters on the sign-in and home pages send a visitor off the site, and whether a marker typed into search boxes comes back in the page unescaped. The OWASP ZAP baseline scan, when Docker runs, spiders the site unauthenticated for two minutes and applies its passive rules (`zaproxy/zap-stable zap-baseline.py`, a local address reached as `host.docker.internal`); its alerts join the list with their risk, places and evidence, its passed rules are listed too, and its HTML report opens from the page. Nothing is attacked or saved. High and Medium findings become bug drafts, cleared by a later scan that no longer finds them; Gate 5 reads the stage as green when the latest scan has nothing High or Medium. Earlier scans stay listed and can be removed.
9. **Bugs and reports.** Failed cases, failed triggers, failed API tests, user-story flows that differ and security findings become drafts. A person confirms a draft (reproducing it unless it is Low), which logs the bug and sends it through the chosen connection. Send report sends the pass and fail result of every case on the latest build through the MCP connector.

## Connections per flow

Settings lists what Claude Code has connected: which skills fit which step, which plugins are enabled, and the state of each MCP server. Each flow picks its own connection there or on its page. A picker offers only skills that fit that step; the mapping is in `src/lib/skillmap.ts`.

- **Claude:** `ANTHROPIC_API_KEY` if set, otherwise this machine's Claude Code login.
- **Claude plugin skills:** Claude follows the skill using your login. Skills get no shell or write tools here, so skills that need them are listed as not used by a step.
- **ChatGPT:** through the Codex CLI after `npm i -g @openai/codex` and `codex login`.
- **Chrome extension (execution only):** needs Claude in Chrome connected. A run stays on the build's QA URL and marks results as AI, so P1 cases still need a person to verify.
- **MCP connector (bugs only):** a Streamable HTTP MCP server with an optional bearer token. Connect in Settings, choose one tool for bugs and one for the report, and adjust their argument templates. Servers that require a browser OAuth sign-in are not supported.

## CI integration

Playwright JSON reporter:

    npx playwright test --reporter=json > results.json
    curl -X POST http://localhost:3100/api/import/playwright \
      -H "Content-Type: application/json" -H "X-Release: Sprint 24" -H "X-Build: 1.24.3" \
      -H "X-Import-Token: $IMPORT_TOKEN" --data-binary @results.json

Newman:

    newman run collection.json -e qa.json -r json --reporter-json-export newman.json
    curl -X POST http://localhost:3100/api/import/newman \
      -H "Content-Type: application/json" -H "X-Release: Sprint 24" -H "X-Build: 1.24.3" \
      -H "X-Import-Token: $IMPORT_TOKEN" --data-binary @newman.json

Each import records an automation run (used for the stability metric). If `X-Build` is given and a test title contains a TC ID (for example `PAY-VR-203-004 submits a payment`), that case's execution on the build is marked Pass or Fail, executed by AI, and the case is flagged automated.

## Bug webhook

Every logged bug is POSTed as JSON to `BUG_WEBHOOK_URL` with an optional bearer token. The payload shape is shown on the Settings page. Failed pushes can be resent from the bug list.

## Thresholds

Edit `src/lib/workflow.ts` to change: P1 pass rate (95%), automation stability (95% over last 10 runs), automation coverage of P1 regression (80%), reopen rate max (10%), mean time to fix Critical/High (24 h).

## Notes

- No login is built in. Run it inside your network or put it behind your existing SSO or reverse-proxy auth.
- Nothing connects to any external tool automatically. Claude, the webhook and the CI imports are each off until you provide the key, URL or token.
- The app was built and compiled in a sandbox without network access to Prisma's engine downloads, so `npm run build` was not executed end to end there. Run `npm install && npm run build` once locally; if a type error appears in a Prisma call, it will be a one-line fix and the file and line are printed.
